# 선잘알 V1 SLI/SLO 설계

- 문서 상태: M5 설계 완료, 측정 구현 대기

## 1. 결론

선잘알 V1은 아래 세 가지를 서비스 수준의 기준으로 삼는다.

| 우선순위 | 사용자가 기대하는 것 | SLI | 잠정 SLO | 현재 상태 |
|---:|---|---|---:|---|
| 1 | 언제든 서비스와 API에 접근할 수 있다 | 유효 요청 성공률 | 99.5% 이상 | 로그 보강 필요 |
| 2 | 상품을 기다림 없이 탐색할 수 있다 | 핵심 읽기 API 응답시간 | 95% ≤ 500ms, 99% ≤ 1,000ms | 상품 목록만 부하 검증 |
| 3 | 로그인 후 핵심 읽기 흐름을 끝낼 수 있다 | Synthetic Journey 성공률 | 99.0% 이상 | Monitor·Fixture 필요 |

수치는 V1의 단일 EC2·단일 DB 구조와 현재 부하 테스트 결과를 바탕으로 정한 **잠정값**이다.

## 2. 범위와 사용자 관점

### 2.1 현재 SLO에 포함하는 기능

현재 운영 Backend에 실제 Controller가 존재하는 흐름만 포함한다.

| 사용자 여정 | 관련 경로 | 사용자 성공 조건 |
|---|---|---|
| 서비스 진입 | `GET /`, 정적 Asset | 앱 화면을 불러올 수 있음 |
| 로그인 | `POST /api/auth/login` | 정상 계정으로 Access Token을 받음 |
| 상품 탐색 | `GET /api/products/categories`, `/api/products`, `/api/products/{id}` | 목록과 상세가 유효한 데이터로 이어짐 |
| 선물 이력 확인 | `GET /api/gifts/sent/**`, `/api/gifts/received/**` | 본인의 목록과 상세를 확인함 |

### 2.2 아직 SLO에 포함하지 않는 기능

- 맞춤 추천과 비선호 카테고리 반영
- 친구 검색·관리
- 선물 사전검증·생성·결제
- 회원가입

이 기능들은 제품 목적상 중요하지만 현재 Backend의 운영 API 구현과 관측 경로가 완성되지 않았다.
API가 출시되면 28일을 기다리지 말고 해당 Journey를 Synthetic Check와 SLI 분류에 추가한다.

### 2.3 SLO와 구분하는 항목

- `/api/health` 성공은 프로세스 상태 확인용이며 사용자 성공을 대신하지 않는다.
- EC2 CPU·Memory, JVM Heap, DB Connection은 원인 진단 지표이지 SLI가 아니다.
- k6 Threshold는 배포 전 성능 합격선이며 28일 운영 SLO 달성 증거가 아니다.
- Portainer Live Stats는 현재 상태 확인 수단이며 장기 SLI 원장이 아니다.

## 3. SLI 명세

### SLI-1. 사용자 경계 가용성

사용자가 Nginx에 보낸 유효한 요청 중 서비스가 정상 응답한 비율을 측정한다.

```text
가용성 = 좋은 요청 수 / 유효 요청 수 × 100

유효 요청 = 전체 요청 - 제외 요청
좋은 요청 = 유효 요청 중 기대한 2xx 또는 3xx 응답
나쁜 요청 = 유효 요청 - 좋은 요청
```

| 항목 | 정의 |
|---|---|
| 측정 위치 | 사용자 경계인 Nginx Access Log |
| 집계 단위 | 전체 서비스와 `login`, `products`, `gift-history` 경로군을 각각 집계 |
| 나쁜 이벤트 | Nginx에서 관측한 5xx와 499. 연결·TLS·DNS 실패는 외부 Synthetic SLI에서 탐지 |
| 제외 | `/api/health`, 내부 Probe, 명시된 k6 User-Agent, 정적 Source Map, 명백한 잘못된 입력의 4xx |
| 별도 추적 | 401/403/404/409/429 비율. SLO 분모에서는 제외하되 급증을 숨기지 않음 |
| 집계 기간 | rolling 28일 |
| 잠정 SLO | 99.5% 이상 |

4xx를 모두 성공으로 계산하지 않는다. 사용자의 잘못된 요청은 제외하되, 배포 결함으로 정상
사용자에게 발생한 4xx는 Incident 검토에서 나쁜 이벤트로 재분류한다. Nginx Log만으로 원인을
구분할 수 없는 동안에는 4xx 경보와 Backend 오류 코드를 함께 확인한다.

### SLI-2. 핵심 API 응답시간

성공한 핵심 읽기 요청 중 사용자 경계에서 목표 시간 안에 끝난 비율을 측정한다.

```text
빠른 요청 비율(T) = request_time ≤ T인 좋은 요청 수 / 좋은 요청 수 × 100
```

| 항목 | 정의 |
|---|---|
| 측정 위치 | Nginx `$request_time` |
| 대상 | 상품 카테고리·목록·상세, 보낸/받은 선물 목록·상세 |
| 분리 집계 | 전체 값 외에 `endpoint_group`별 p50/p95/p99와 최대값 확인 |
| 제외 | SLI-1 제외 요청, 실패 응답, 승인된 부하 테스트 |
| 집계 기간 | rolling 28일 |
| 잠정 SLO | 좋은 요청의 95%는 500ms 이내, 99%는 1,000ms 이내 |
| 보조 진단 | `$upstream_response_time`으로 Nginx/Network와 Backend 지연을 구분 |

전체 백분위만 보면 특정 API 장애가 가려질 수 있다. 전체 SLO 판정과 별개로 경로군 하나라도
`p95 > 500ms`가 15분 지속되면 조사한다.

### SLI-3. 핵심 사용자 여정 성공률

운영 외부에서 실제 사용자와 같은 경로를 주기적으로 실행해, 모든 필수 단계와 응답 계약을
완료한 비율을 측정한다.

```text
Journey 성공률 = 모든 필수 단계를 완료한 실행 수 / 시작한 실행 수 × 100
```

| 항목 | 정의 |
|---|---|
| 실행 위치 | 운영 EC2 외부의 Synthetic Monitor |
| 실행 주기 | 5분마다, timeout 5초/요청 |
| Journey | 로그인 → 카테고리 → 상품 목록 → 상품 상세 → 보낸 선물 목록·상세 → 받은 선물 목록·상세 |
| 성공 조건 | 각 단계 기대 Status, JSON Contract, 앞 단계 ID로 다음 상세 조회 성공 |
| 실패 조건 | 한 단계라도 연결 실패, timeout, 잘못된 Status 또는 Contract 불일치 |
| 테스트 데이터 | 개인정보가 없는 전용 계정, 보낸/받은 선물 각 1개 이상 |
| 집계 기간 | rolling 28일 |
| 잠정 SLO | 99.0% 이상 |

여정의 Think Time은 사용자 행동을 흉내 내는 부하 테스트에는 사용하지만, 가용성 Synthetic
Monitor에는 넣지 않는다. Monitor 자체 장애가 확인된 실행은 근거를 남기고 제외한다.

### SLI-4. Frontend 진입 성공률(운영 Guardrail)

`GET /`이 200을 반환하고 HTML에 예상 Build Marker가 존재하며, 핵심 정적 Asset 하나를 내려받을
수 있는지 1분마다 확인한다. 목표는 99.5%지만, 초기에는 요청 기반 SLO의 보조 Guardrail로
운영한다. API가 정상이어도 화면 배포가 깨지는 경우를 탐지하기 위한 지표다.

## 4. 목표값과 근거

### 4.1 가용성 99.5%

| 기준 | 28일 오류 예산 참고값 |
|---|---:|
| 시간 기반 가용성으로 환산할 경우 | 201분 36초(요청 기반 SLI의 직접 허용 시간은 아님) |
| 현재 예상 요청 630건/일로 환산 | 약 88건/17,640건 |

V1은 Frontend, Backend, MySQL이 단일 EC2에서 실행되고 자동 확장·다중 AZ·자동 Failover가 없다.
이 상태에서 99.9%(28일 약 40분)를 약속하는 것은 복구 구조와 맞지 않는다. 99.5%도 느슨한
목표는 아니며, V2에서 이중화와 자동 복구를 검증한 뒤 99.9% 상향을 검토한다.

### 4.2 응답시간 500ms/1,000ms

상품 목록 Load 시험은 최대 30 RPS 구간을 포함한 45,510개 요청에서 실패 없이
`p95 133.7ms`, `p99 319.97ms`를 기록했다. 따라서 500ms/1,000ms는 현재 확인된 여유를
유지하면서 다른 API와 실제 운영 편차를 수용하는 초기선이다.

다만 28.11초 최대값과 부하 발생기 시간 불일치가 있었고, 상품 목록 외 API는 같은 수준으로
검증되지 않았다. 이 숫자는 운영 데이터와 전체 Journey Baseline으로 재검토한다.

### 4.3 Journey 성공률 99.0%

인증 읽기 Smoke는 실행된 5개 API에서 성공했지만, Test Account에 선물 이력이 없어 두 상세
단계를 검증하지 못했다. Synthetic Monitor와 Fixture가 준비될 때까지 이 SLO는 **정의됨/미측정**
상태이며 출시 차단 기준으로 사용하지 않는다.

## 5. 오류 예산과 운영 정책

가용성 SLO 99.5%의 오류 예산은 28일 유효 요청의 0.5%다.

```text
오류 예산 = 유효 요청 수 × (1 - 0.995)
오류 예산 소진율 = 누적 나쁜 요청 수 / 오류 예산 × 100
```

| 상태 | 조건 | 조치 |
|---|---|---|
| 정상 | 예산 소진 < 50% | 계획된 배포 진행, 주간 검토 |
| 주의 | 예산 소진 ≥ 50% | 실패 경로 분석, 고위험 변경에 추가 검증 |
| 위험 | 예산 소진 ≥ 75% | 기능 배포보다 안정성 작업 우선, 배포 승인 강화 |
| 소진 | 예산 소진 ≥ 100% 또는 SLO 미달 | 긴급 수정 외 배포 중단, 원인·재발 방지 검토 |

월말까지 기다리지 않도록 빠른 소진도 감시한다.

| 빠른 소진 신호 | 의미 | 초기 대응 |
|---|---|---|
| 최근 1시간 실패율 ≥ 5% | 10배 이상 속도로 예산 소진 | 즉시 확인·장애 판단 |
| 최근 6시간 실패율 ≥ 2% | 지속 장애 또는 반복 결함 | 당일 원인 분석 |
| 외부 Check 2회 연속 실패 | 사용자 접근 불가 가능성 | 다른 위치 재확인 후 대응 |

초기 경보값은 운영 데이터가 없는 상태의 시작점이다. 실제 Noise와 탐지 시간을 2주 후 검토한다.

## 6. 측정 데이터 계약

### 6.1 Nginx Access Log 필수 필드

| 필드 | 목적 |
|---|---|
| UTC Timestamp | 시간 구간 집계 |
| Request Method | 동일 경로의 읽기/쓰기 구분 |
| 정규화된 Route 또는 URI | Endpoint Group 분류 |
| Status | 좋은/나쁜 이벤트 판정 |
| `$request_time` | 사용자 경계 Latency |
| `$upstream_response_time` | Backend 처리 지연 분리 |
| `$request_id` | Nginx와 Backend Trace 연결 |
| User-Agent | Probe와 승인된 부하 테스트 제외 |
| Upstream Address/Status | Proxy·Backend 실패 원인 구분 |

Query String, Authorization, Cookie, 비밀번호, Access/Refresh Token과 개인정보는 로그에 남기지
않는다. 상품·선물 ID가 포함된 실제 URI 대신 가능하면 정규화된 Route를 집계한다.

### 6.2 데이터 원천과 보존

| 데이터 | 원천 | 최소 보존 | 용도 |
|---|---|---:|---|
| Edge 요청 | Nginx Access Log → CloudWatch Logs | 90일 | 가용성·응답시간 원장 |
| 애플리케이션 요청 | Backend 구조화 로그 | 30일 | 오류 코드·Trace·경로 원인 분석 |
| 외부 확인 | Synthetic Monitor 결과 | 90일 | 무트래픽 시간 가용성·Journey |
| 자원 지표 | EC2/CloudWatch Agent, Docker/JVM/DB | 30일 | 장애 원인과 용량 분석 |
| 배포·장애 기록 | 배포 이력과 Incident 기록 | 1년 | SLI 변화 상관관계·회고 |

원본 로그와 Dashboard 수치가 다르면 원본 Edge Log를 가용성·Latency의 기준으로 삼는다.

## 7. Dashboard와 경보 요구사항

Dashboard는 같은 1분 시간축에 아래 항목을 배치한다.

1. 전체 및 경로군별 요청 수, 2xx/3xx/4xx/5xx/499 비율
2. 전체 및 경로군별 p50/p95/p99 `$request_time`
3. Nginx와 Backend의 502/503/504, Container Restart 수
4. Synthetic Frontend와 핵심 Journey 성공 여부
5. EC2 CPU·Memory·Disk, JVM Heap/GC, Hikari Connection, MySQL Connection
6. 배포 시각과 Incident 구간 Annotation
7. rolling 28일 SLO 달성률, 남은 오류 예산, 예산 소진 속도

사용자 영향 경보와 원인 지표 경보를 구분한다. CPU가 높다는 이유만으로 장애라고 선언하지
않고, 사용자 SLI 악화와 결합해 우선순위를 판단한다.

## 8. 데이터 제외와 변경 관리

다음 조건을 모두 만족해야 SLO 집계에서 제외할 수 있다.

- 사전에 승인된 부하 테스트 또는 유지보수이며 식별 가능한 User-Agent/시간 구간이 있음
- 외부 Monitor 자체 장애처럼 선잘알이 통제하지 못하는 측정 오류가 증명됨
- 제외 이유, 시작·종료 시각, 요청 수, 승인자를 Incident 기록에 남김

계획된 배포, 서버 재시작, DB Migration은 사용자에게 실패를 보였다면 원칙적으로 제외하지
않는다. SLO 숫자·분모·제외 조건을 바꿀 때는 변경일을 기록하고 이전 기간을 소급 수정하지 않는다.

## 9. 배포 전 Release Gate

| 항목 | 현재 기준 | 현재 증거 |
|---|---:|---:|
| 상품 목록 최대 부하 | 30 RPS 20분 유지 시나리오 완료 | 완료 |
| HTTP 실패율 | < 1% | 0% |
| Business 오류율 | < 1% | 0% |
| p95 / p99 | < 500ms / < 1,000ms | 133.7ms / 319.97ms |
| Dropped Iteration | 0 | 0 |

이 결과는 상품 목록 API의 해당 시험 조건만 증명한다. 인증 Journey, 쓰기 API, 장애 복구,
서비스 전체 최대 처리량과 28일 SLO 달성을 증명하지 않는다.

## 10. 구현 순서와 완료 조건

| 순서 | 작업 | M5 관점의 완료 증거 |
|---:|---|---|
| 1 | Nginx 구조화 Access Log와 Request ID 추가 | 필수 필드가 실제 요청 1건에 기록됨 |
| 2 | CloudWatch Logs 전송·보존 설정 | 운영 Log Group에서 검색 가능 |
| 3 | SLI Query/Metric Filter 작성 | 임의 2xx·4xx·5xx 표본이 정의대로 분류됨 |
| 4 | Frontend 및 Journey Synthetic Check 구축 | 외부에서 주기 실행되고 실패가 기록됨 |
| 5 | Dashboard·Alarm 연결 | Test Alarm이 담당 채널에 도착함 |
| 6 | 2주 데이터 품질 검토 | 누락·중복·제외 조건과 Noise 수정 |
| 7 | 28일 SLO 검토 | 실제 달성률과 오류 예산으로 잠정값 승인/보정 |

측정 구현 전 문서 상태는 **설계 완료/운영 검증 전**이다. 1~5가 끝나야 “SLI 수집 중”,
28일 검토 후에야 “SLO 운영 중”으로 바꾼다.

## 11. 검토 및 승인

| 역할 | 확인할 내용 | 담당자 | 상태 |
|---|---|---|---|
| Product/Frontend | 핵심 Journey와 사용자가 느끼는 성공 조건 | 미정 | 검토 필요 |
| Backend | Endpoint 분류, 정상 4xx, 오류 코드, Test Fixture | 미정 | 검토 필요 |
| Cloud/운영 | 로그·집계·Dashboard·Alarm·오류 예산 | 미정 | 설계 완료 |

승인은 목표 숫자만이 아니라 측정식, 분모, 제외 조건, 집계 기간과 검토일을 함께 대상으로 한다.

## 12. 알려진 제약과 다음 결정

### 확인된 사실

- V1은 단일 EC2에서 Frontend, Backend와 MySQL 컨테이너를 실행한다.
- 현재 Actuator는 Health만 노출하고 Prometheus/Micrometer 지표는 노출하지 않는다.
- Nginx 설정에는 SLI 계산에 필요한 구조화 Log Format이 없다.
- 상품 목록 최대 30 RPS 시험은 통과했지만 전체 사용자 여정의 부하 결과는 없다.

### 아직 확인할 것

- 4xx 중 정상 사용자 결함을 나타내는 Backend Error Code 분류
- 운영 Traffic의 Endpoint 비율과 실제 동시 사용자 수
- 선물 상세가 있는 Synthetic 전용 계정과 Fixture 유지 방법
- CloudWatch Logs/Metric/Alarm 비용과 최종 보존 기간
- V2에서 99.9%를 가능하게 할 이중화·자동 복구·RTO

### 보류한 대안

| 대안 | 현재 제외 이유 |
|---|---|
| Health Check만 가용성으로 사용 | 사용자 기능과 인증·데이터 조회 성공을 보장하지 못함 |
| Portainer만으로 SLI 운영 | 장기 시계열·SLO 계산·외부 사용자 관점이 부족함 |
| k6 결과를 월간 SLO로 사용 | 통제된 단기 시험이며 운영 기간과 실제 Traffic을 대표하지 않음 |
| 시작부터 99.9% 약속 | 단일 장애 지점과 수동 복구 구조에서 근거가 부족함 |
