# 부하 시험 Fixture

| 파일 | 대상 | 내용 |
| --- | --- | --- |
| `v1-load-test-fixture.sql` | V1 Develop | 사용자 500명(`loadtest001~500`), 친구·받은 선물 |
| `v2-staging-load-test-fixture-10k.sql` | V2 Staging(스키마 V12) | 기존 500명은 유지하고 501~10000번을 추가해 총 10,000명 |
| `v2-staging-load-test-fixture-10k-cleanup.sql` | V2 Staging(스키마 V12) | 501~10000번과 그 관계 데이터만 삭제 |

## 생성 규칙 (10,000명 확장)

- 신규 계정: `loadtest00501~10000@seonjalal.invalid`, 비밀번호는 기존 Fixture와 같은 bcrypt 값(평문은 Backend Seed 정책의 `Test1234!`)
- Persona: 번호 끝자리 0~4 Light(친구 1~3, 받은 선물 1~2), 5~8 Normal(5~15, 3~10), 9 Heavy(30~100, 30~100). 기존 비율 50/40/10 유지
- 친구·발신자: 번호에 총원과 서로소인 소수(7919, 6007)를 곱한 모듈러 규칙. 난수 없음, 같은 입력이면 같은 결과, 자기 자신·중복 쌍 없음
- 상품 카탈로그와 기존 500명 데이터는 변경하지 않음

## 실행 조건

- 스키마가 Flyway V12일 때만 실행. V13 이후에는 신규 Table·NOT NULL 칼럼이 생겨 그대로 쓸 수 없음
- 기존 Fixture 500명이 정확히 있고 501번 이상이 없어야 함(Guard). 아니면 `chk_load_test_base_exact` 오류로 중단되며 데이터는 변경되지 않음
- Production에서는 실행하지 않음. 실행 전에 DB 스냅샷 필수
- V13 이후 초기화는 Fixture 적재 직전 스냅샷 복원 기준(cleanup 파일은 V12 전용)

## 로컬 검증 기록 (MySQL 8.4.11 컨테이너, 스테이징과 같은 V1~V12 + 기존 500명 상태)

- 적재 후 사용자 10,000명(신규 9,500), 친구 114,943, 받은 선물 97,950, 약관 동의 50,045, 중복 친구 쌍 0, 자기 자신 친구 0
- cleanup 후 적재 이전 행 수(사용자 512, 친구 5,718, 선물 4,864, 약관 동의 2,545)로 정확히 복귀, 재적용·cleanup 반복 가능
- 이후 V13~V35 적용 시 오류 없음. 크레딧 계정·거래·수신자 프로필이 사용자 수만큼 생성됨
- 위 수치는 로컬 컨테이너에서 측정한 값이며 RDS(Multi-AZ, `db.t4g.small`)의 소요시간이 아님

## 한계

- 균일한 모듈러 분포라 인기 상품 쏠림·친구 수 분포의 꼬리가 실제 서비스와 다름. 캐시·인덱스 접근 패턴에 민감한 시험 결과는 이 한계를 함께 기록
